## Context

`ScriptCollection` already has a Vega-Lite based diagramming convention (see `ScriptCollectionCore.generate_chart_diagram`,
`ScriptCollectionCore.add_tooltips_to_chart_diagram` and the LoC-diagram generated by
`TFCPS_CodeUnit_BuildCodeUnits.__generate_loc_diagram`): a Vega-Lite JSON specification is built as a `dict`, written to a
`.json`-file, and can optionally be rendered to `.svg` via the `vl2svg`-CLI (a `vega-lite`-npm-package already available
in the build-image). This change reuses that convention for a new, self-contained pair of classes instead of extending
`ScriptCollectionCore` itself, because git-history-analysis and diagram-generation are a cohesive, independently
reusable unit that does not depend on any other `ScriptCollectionCore`-state. See proposal.md for the "why".

## Goals / Non-Goals

**Goals:**
- Provide `RepositoryHistoryAnalyzer` (reads git history, returns structured data) and `RepositoryDiagramGenerator`
  (turns that data into a Vega-Lite specification), matching exactly this call-shape:
  `RepositoryDiagramGenerator().generate_committer_timeline(RepositoryHistoryAnalyzer().get_git_history_data(repo, GitHistoryScale.Week), target_file)`.
- Keep the two classes independently testable (`RepositoryHistoryAnalyzer` needs a real/temporary git-repository;
  `RepositoryDiagramGenerator` only needs plain data and does not call `git` at all).

**Non-Goals:**
- Rendering the generated specification into an image is not implemented as part of the two new classes (see
  proposal.md); it stays a manual/consumer-side step using the already-existing `generate_chart_diagram`.
- No `.mailmap`-specific handling beyond what `git shortlog`/`git log` already do natively.
- No support for showing more than one email-address per committer, even if a committer used several addresses. In
  that case, `git shortlog -n -s -e` shows the first one it encounters for the display name; that is treated as an
  existing git-behavior and not corrected.

## Decisions

### Data model
Two dataclasses plus one enum, defined in `RepositoryHistoryAnalyzer.py`:
- `GitHistoryScale(Enum)`: `Day`, `Week`, `Year` - controls the bucket-granularity of `get_git_history_data`.
- `CommitterActivityDataPoint`: `committer: str`, `bucket: str`, `commit_count: int`. `bucket` is a pre-formatted,
  chart-ready label (`YYYY-MM-DD`, ISO-week `YYYY-Www`, `YYYY`, a weekday-name, or a zero-padded hour `"00"`..`"23"`,
  depending on which analyzer-method produced it).
- `CommitterActivityData`: `committers: list[str]` (order and identities exactly as `git shortlog -n -s`),
  `committer_emails: dict[str, str]` (committer name -> email), `data_points: list[CommitterActivityDataPoint]`.

All four `RepositoryDiagramGenerator.generate_*`-methods take a `CommitterActivityData` and a `target_file: str`
and are otherwise independent of how the data was produced - this is what "analogous" for the weekday/hour
generate-methods means in practice: same generator-side handling, different analyzer-side data-source.

### `RepositoryHistoryAnalyzer` methods
- `get_committers(repository_path) -> list[str]`: parses `git shortlog -n -s HEAD`.
- `get_committer_emails(repository_path) -> dict[str, str]`: parses `git shortlog -n -s -e HEAD`.
- `get_git_history_data(repository_path, scale: GitHistoryScale) -> CommitterActivityData`: parses
  `git log --pretty=format:%cI<TAB>%cn` (once), buckets each commit's `%cI`-timestamp (kept in the commit's own
  recorded UTC-offset, not converted to another timezone) by `scale`, and combines it with `get_committers` /
  `get_committer_emails`.
- `get_commits_per_weekday_data(repository_path) -> CommitterActivityData`: same commit-log parsing, bucketed by
  weekday-name (`Monday`..`Sunday`) instead of by calendar period.
- `get_commits_per_hour_data(repository_path) -> CommitterActivityData`: same commit-log parsing, bucketed by
  zero-padded hour-of-day (`"00"`..`"23"`).

Only buckets with at least one commit are included (no zero-filling for empty periods/weekdays/hours), consistent
with how the existing LoC-diagram only plots the data-points it actually has.

`get_git_history_data`/`get_commits_per_weekday_data`/`get_commits_per_hour_data` each run their own `git log`
subprocess-call rather than sharing one cached call, matching this codebase's existing style of small,
independently-callable `ScriptCollectionCore`-methods (e.g. `get_all_commits_in_git_repository`) over an internal
cache.

### `RepositoryDiagramGenerator` methods
- `generate_committer_timeline(data, target_file)`, `generate_commits_per_weekday_chart(data, target_file)`,
  `generate_commits_per_hour_chart(data, target_file)`: all three build the same kind of Vega-Lite spec (one
  `line`-mark with `point: true`, `x` = bucket as `ordinal` - with an explicit `sort`-order for weekday/hour so
  "Monday".."Sunday"/"00".."23" are not sorted alphabetically -, `y` = `Commits` as `quantitative`, `color` =
  `Committer`). Only the bucket-field's title/sort-order differs between the three, so they share one private
  builder-method.
- `generate_committer_pie_chart(data, target_file)`: `arc`-mark, `theta` = summed `Commits` per committer,
  `color` = `Committer`; a `joinaggregate`+`calculate`-transform computes each committer's `Share` (0..1) for the
  percentage-tooltip, formatted with Vega-Lite's `"format": ".1%"`.
- Both files are written with `json.dump(..., indent=2, ensure_ascii=False)`, matching the existing LoC-diagram's
  formatting.

### Point-tooltip ("exact commit-count"/"exact percentage")
Achieved with a plain Vega-Lite `encoding.tooltip`-array (`Committer`, bucket-field, `Commits`, and - for the
pie-chart - `Share` formatted as `.1%`). This is the standard, directly-supported Vega-Lite mechanism; no extra
trick is required.

### Legend-hover email-tooltip
Vega-Lite's own tooltip-encoding only applies to marks, not to legend-entries, so showing a committer's
email-address when hovering their *name in the legend* needs one additional, deliberate construct:
1. A `datasets.committerEmails` array (`[{"Committer": <name>, "Email": <email>}, ...]`) is added to the spec
   alongside the chart's own `data`.
2. The `color`-encoding's `legend.encode.labels.update.tooltip` is set to the Vega expression
   `pluck(data('committerEmails'), 'Email')[indexof(pluck(data('committerEmails'), 'Committer'), datum.value)]`,
   which looks up the hovered legend-label's (`datum.value`, the committer name) matching email via the two
   built-in Vega expression-functions `pluck`/`indexof` (Vega's expression-language has no arbitrary
   lambda/`.find()`, so a lambda-free array/index lookup is used instead).
   This is a `legend.encode`-passthrough, a documented Vega-Lite mechanism for customizing legend
   marks/labels/entries with raw Vega mark-encodings; it is not a Vega-Lite core encoding channel.
3. Verified to compile without error using the `vl2svg`-CLI already available in this environment (`vega-lite@6.4.1`)
   against a minimal two-committer spec built the same way; the actual hover-behavior itself only manifests when
   the specification is rendered by the interactive Vega(-Lite) runtime (a browser via `vega-embed`, for example),
   not in a static `.svg`/`.png`-export - consistent with the "diagram-generation produces a specification, not a
   rendered image"-requirement in the spec.

### Where the new files live
`ScriptCollection/ScriptCollection/RepositoryHistoryAnalyzer.py` and
`ScriptCollection/ScriptCollection/RepositoryDiagramGenerator.py`, next to the other single-purpose top-level
classes of this codeunit (e.g. `SCLog.py`, `ProgramRunnerBase.py`). `RepositoryHistoryAnalyzer` instantiates its own
`ScriptCollectionCore` in `__init__` (`self.sc = ScriptCollectionCore()`), matching the constructor-pattern already
used by `TFCPS_CodeUnit_BuildCodeUnits` and others, and uses `self.sc.run_program_argsasarray("git", [...], repository_path)`
for every git-invocation instead of calling `subprocess`/`git` directly. `RepositoryDiagramGenerator` does not need a
`ScriptCollectionCore`-instance at all (it never shells out).
Corresponding tests: `ScriptCollectionTests/test_RepositoryHistoryAnalyzer.py` (against a temporary git-repository
built with a handful of scripted commits, analogous to the existing `test_file_is_git_ignored_3`-pattern) and
`ScriptCollectionTests/test_RepositoryDiagramGenerator.py` (pure data-in/JSON-out, no git needed).

## Risks / Trade-offs

- [The `legend.encode`+`pluck`/`indexof` email-tooltip is an advanced, less commonly used Vega-Lite/Vega
  construct] → Mitigated by keeping it isolated in one small private helper-method used by all four generators, and
  by documenting the mechanism (this section) so it is not "magic" if it ever needs to change; compiled successfully
  against the `vega-lite`-version installed in this environment.
- [`git shortlog`'s own name/email-grouping is a black box (its exact merge-heuristic for multiple emails per name
  is a git-internal, undocumented-in-detail behavior)] → Out of scope to fix (see Non-Goals); the two classes
  faithfully reflect whatever `git shortlog -n -s [-e]` reports.
- [Bucketing by each commit's own recorded UTC-offset (not a normalized single timezone) means two committers in
  different timezones may show a commit as "different weekday/hour" even if it happened at the same real-world
  moment] → Accepted as the more useful interpretation for a "when do committers typically commit" diagram (their
  own local time-of-day), and documented in this file so it is a deliberate choice, not an oversight.
