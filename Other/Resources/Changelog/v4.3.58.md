# Release notes

## Breaking changes

- `<repository>/.ScriptCollection/ProductInformation.xml` must now always contain a `requiredenvironmentvariables`-element. A product whose build does not need any environment-variable declares it empty (`<cps:requiredenvironmentvariables></cps:requiredenvironmentvariables>`). This makes the dependency on environment-variables an explicit statement of every product instead of information which can be absent by accident. The corresponding `projectinformation.xsd` of the CommonProjectStructure was extended accordingly.

## Changes

- reworked the custom pre-codeunit-build-scripts: `~/.ScriptCollection/TFCPS/CustomPreCodeUnitBuildScript.py` runs at the beginning of a build on the host, `CustomPreCodeUnitBuildScriptForContainer.py` runs on the host before the build-container is started and `CustomPreCodeUnitBuildScriptInContainer.py` is mounted read-only into the container and runs there at the beginning of the build
- removed `<repository>/.ScriptCollection/RequiredEnvVariables.csv`
- added the possibility to declare required environment-variables in `<repository>/.ScriptCollection/ProductInformation.xml` whose values are resolved from `~/.ScriptCollection/TFCPS/EnvironmentVariables.csv` and set for every codeunit-build (also when a single codeunit is built directly). When the build runs in a container only the names of the variables are passed as arguments, so a value does not appear in the log or in the process-list of the host
- a value which is not defined in `~/.ScriptCollection/TFCPS/EnvironmentVariables.csv` is taken from the environment of the build-process, which is how a build-pipeline provides it from its own secret-store. Because the configuration-file is looked up in the configuration-folder, a build-container which gets that folder mounted resolves the values exactly like a build on a host does; the article "Build-runner-configuration" describes that setup for self-hosted GitLab- and GitHub-runners
- the value-resolution is also available without a repository-declaration (`TFCPS_Tools_General.resolve_environment_variable(s)`), so a tool which runs inside the build-container can obtain a secret with the same mechanism instead of reading a file at a fixed location or the environment on its own
- added a secret-scan for OCI-images (image-history, image-environment-variables, image-labels and the content of the image-layers), because the betterleaks-scan of the repository can not find secrets which are only contained in a built image. It runs as part of `scbuildcodeunits` and is also available as `scsearchforsecretsinimage` to scan any locally available image
- reimplemented the configuration of custom NuGet-sources based on the required-environment-variables-mechanism: a source is declared by the environment-variables `Dependency_CSharp_<sourcename>_URL`, `_Username` and `_Password`, and is registered before every .NET-codeunit-operation (build, testcases, linting, dependency-update). An already registered source with the same url is updated instead of being registered a second time, and sources which are not declared are never changed. This replaces `~/.ScriptCollection/TFCPS/CustomC#Dependencies.csv`, which is not used anymore
- removed the configuration of custom PyPI-indexes (`~/.ScriptCollection/GlobalCache/Pip`); it is not reimplemented yet
- the dependency-update (`scupdatedependencies`) now updates the dependencies while the codeunits are built regularly instead of using an own reduced build-process. It therefore gets all preparation-steps of a build (required environment-variables, custom pre-codeunit-build-script and the package-sources), which especially makes the dependency-update work inside a build-container. For this the codeunit-build got an internal extension-point (`TFCPS_BuildCodeUnitsHook`)
