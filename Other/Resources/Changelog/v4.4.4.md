# Release notes

## Changes

- aded helper for visual regression tests in tfcps
- the helper for visual regression tests now preserves the expected, the actual and the differing screenshot of every failed testcase in "Other/Artifacts/VisualRegressionTestFailures/&lt;timestamp&gt;", because playwright empties its output-folder at the beginning of every run, so the screenshots of a testcase which fails only sporadically were lost with the next run
- added the enum "TestKind" (ScriptCollection.TestKind), which is generated from the TestKind-enum of GRYLibrary, so both products use the same test-kinds (same names, same comments and same values)
- the helper for visual regression tests got the two checks "check_layouts_are_similar" and "check_screenshots_are_similar", which compare the browsers with each other. Until now every screenshot was only ever compared with the baseline-screenshot of its own browser, so a page which looks different in one browser than in the others stayed unnoticed. "check_layouts_are_similar" compares the position and the size of every element of every checked page (which the testcases write down while they run); it is the check which detects a misplaced part of a page. "check_screenshots_are_similar" compares the baseline-screenshots themselves after downscaling them; it is coarse on purpose and detects a missing picture, a different page-height or a completely different page. The reason for the split is that the engines rasterize text differently: even on a page which looks the same thousands of pixels differ, so a pure comparison of the screenshots needs a threshold which is too high to detect a part of a page which moved
- the helper for visual regression tests accepts the parameter "playwright_project" now, which restricts a run to one project of the playwright-configuration (which is one browser). Codeunits whose testcases change the state of the application under test need this: they have to start the application newly for every browser, because otherwise the second browser would find the state which the first one left behind and would therefore see other pages than the first one
- added the functions "start_rtsp_test_stream" and "create_test_stream_video", which generate a video whose picture only shows a number which is counted up once per second (optionally with a further text) and provide it as rtsp-stream respectively as file. This is what makes a testcase which records a stream able to assert what the recording shows at a certain moment, without needing a real camera
- "normalize_invisible_characters" removes a byte-order-mark now and normalizes the line-endings, so a file which was written on windows and a file which was written on linux do not differ anymore only because of that
- implemented the tasks of a maven-codeunit (TFCPS_CodeUnitSpecific_Maven): building the jar, generating the bill-of-materials, the linting with checkstyle, running the testcases including the measurement of the test-coverage, and reading, resolving and updating the dependencies of the pom-file. The maven-project of such a codeunit is expected in "&lt;codeunit&gt;/&lt;codeunit&gt;" and contains its testcases in its own "src/test"-folder, because that is the layout maven defines and the layout jacoco measures the coverage of without further configuration
- implemented the tasks of a rust-codeunit (TFCPS_CodeUnitSpecific_Rust): building the release-artifacts, generating the bill-of-materials, the linting with clippy (a warning of clippy fails the linting), running the testcases with cargo-llvm-cov, and reading, resolving and updating the dependencies of the cargo-file. cargo-llvm-cov writes its coverage-report in the cobertura-format directly, so only the package-name and the paths of the report have to be adapted afterwards
- implemented the missing tasks of a go-codeunit (TFCPS_CodeUnitSpecific_Go): building the executable, generating the bill-of-materials, the linting (go-vet plus the verification that every file is formatted as gofmt formats it, whose result has to be read from the output because "gofmt -l" exits successfully even when it found something), and reading, resolving and updating the dependencies of the go-module-file
- added "convert_jacoco_report_to_cobertura_report", which converts a coverage-report of the jvm-ecosystem into the cobertura-format. The further processing of a coverage-report (the check of the threshold, the html-report and the badges) expects that format, and the tools of the jvm-ecosystem do not write it
- added "convert_go_coverprofile_to_cobertura_report", which converts the coverprofile which "go test -coverprofile" writes into the cobertura-format. Until now the go-codeunit installed the third-party-tool "gocover-cobertura" from its main-branch during the build and piped the coverprofile into it through "sh -c". That made the result of a build depend on the state of a foreign repository at that moment and it did not work on a machine without a posix-shell, which is why the conversion is done here now
- renamed "normalize_line_endings" to "normalize_invisible_characters" and "normalize_line_endings_of_files_in_folder" to "normalize_invisible_characters_of_files_in_folder", because these functions do not only touch the line-endings anymore. This is a breaking change: a caller which uses the former names has to be adapted
- fixed the decorator "check_arguments", which read the parameters of the decorated function with "getfullargspec". That does not follow the chain which "functools.wraps" sets, so above another decorator the check only saw the wrapper, and a wrapper has no named parameters, which means no argument was checked at all. It reads the signature now. Additionally the check does not fail anymore when more arguments are passed than the function has parameters: that is a wrong call, but reporting it belongs to the call itself, whose error-message names the expected and the given amount
- the build of a nodejs-codeunit removes the sourcecode-artifact of the previous run before it starts. That artifact is a copy of the codeunit inside the codeunit and the build-tools do not know that it is only an artifact: ng-packagr for example searches the whole project-folder for "ng-package.json"-files to find the entry-points of the package, finds the copied one and aborts. The copy is written again at the end of the build, so nothing is lost
- added the task "deploy locally" (alias "dl") to the code-workspace, which uninstalls the installed package and installs the wheel of the last build instead. This makes it possible to try out a change with the commandline-tools without releasing the product first
- added skill-descriptions which document the automations of this product and the work with the common project structure, so that an assistant does not have to derive them from the sourcecode
